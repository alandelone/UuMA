## 1. 本轮范围

支持通过对话设置、记录、修改和查回历史。第一批沿用原本的习惯，以后可以增加新习惯。

本轮交付是讨论记录，不启动功能开发、数据迁移、提醒任务或部署。

## 2. 整体职责与架构方向

保留一个 honc 日常管家，在内部区分四类职责：

| 部分 | 职责 |
| --- | --- |
| 工作执行 | 专注回合、开始／暂停／恢复、实际成果、完成标准核对与允许的项目回写 |
| 生活习惯 | 习惯设置、增加／修改／暂停／停用、打卡、数量／次数／时长 |
| 身体记录 | 保存用户主动报告的身体感受和状态，包括不适、疲劳、疼痛、舒服或精神很好 |
| 日记与回看 | 保存日记，按日期查回并汇合工作、习惯和身体记录 |

不同类型的记录可以关联，但保持各自的含义。用户在工作回合中报告一个习惯或身体感受，
不必先结束、暂停或重新启动工作回合。例如「拉伸了十分钟，现在有点累」可以分别形成
习惯记录和身体观察，关联同一条原始消息。

旧 State 0–4 工作状态流程可以保留在工作执行部分；生活记录不以进入该流程为前提。
提醒与记录状态需要持久保存，不依赖模型记忆、当前聊天是否打开或用户是否正在用手机。
具体调度器与消息渠道仍待实施设计。

| 角色／系统 | 保留的所有权 |
| --- | --- |
| 用户 | 习惯、提醒设置、日常报告与项目最终决策 |
| Yonc／项目后端 | 项目计划、任务结构、优先级、验收标准与已接受的项目状态 |
| honc | 日常执行事实、习惯、身体观察、日记、历史查询和提醒状态 |
| Hermes Orchestrator／UuMA | Agent 运行控制、协调和权限 |

## 3. 习惯管理与记录

将三个概念分开：

1. **习惯定义：**名称、描述、记录类型、单位、目标、执行频率和启用状态。
2. **提醒规则：**时间／时间窗口、允许的情境、提醒次数、重要度及已提醒状态。
3. **发生记录：**实际做了什么、发生时间、数量／次数／时长、用户原话与来源。

需要支持增加、修改、暂停、停用或移出当前习惯清单；也需要补记、纠错和历史查询。
停用或修改习惯不抹掉过去的记录。修改目标或提醒规则后，旧记录仍保留当时的归属与上下文。
记录更正保留原始历史，具体版本和更正模型在实施设计时明确。

习惯可采用完成型、计次型、数量型、时长型或文字记录型，日记属于文字记录型习惯。
同一天的多次执行分别保存，例如早餐、午餐、晚餐不能被一个全天布尔值抹平。

「已提醒」「已打卡」「跳过」「未记录」含义不同。没有回复或没有打卡只表示没有记录，
不能推断用户没有做，也不能自动判定习惯完成。

## 4. 已明确的提醒行为

### 4.1 基本规则

- 习惯在其应执行的时间或时间窗口内提醒，默认每个执行实例一次。
- 提醒时间、提醒次数和重要度可设置；增加次数由用户明确修改设置。
- 没有回复不额外催问，重要度不擅自增加提醒次数。
- 晚上不汇总未打卡习惯来补催；晚间日记本身就是一项提醒一次的习惯。
- 同一个执行实例的提前触发与定时触发共享提醒额度，避免重复提醒。
- 身体状态不触发主动的变化追问，例如「好一点了吗」「现在还痛吗」。

固定时间和固定时间窗口均支持，例如 15:00–16:00。
当前支持的情境锚点仅为 **起床后、睡前**；本轮没有扩展饭后、厕所、休息等情境触发。

### 4.2 起床后

默认时间为 **08:00，Asia/Kuala_Lumpur**。

- 用户没有用手机或没有发消息，仍应由后台按默认时间发出提醒。
- 如果用户更早明确表示起床，或明确开始当天计划，则提前触发相关晨间提醒。
- 例如 05:00 或 07:00 已经提前提醒，同一天对应实例到 08:00 不再重复。
- 如果 08:00 已经提醒，用户稍后再报告起床，也不重复提醒同一实例。
- 普通早间消息不自动视为「开始当天计划」，应有明确的起床／新一天开始语义。
- 提醒时间与实际起床时间分开；08:00 提醒不证明用户在 08:00 起床。

### 4.3 睡前与晚间日记

默认时间为 **21:30，Asia/Kuala_Lumpur**。

晚间一次提醒邀请用户写日记，并可以一起记录当天身体状态。
日记打卡与身体观察在消息中可以合并邀请，在数据中仍分别保存并建立关联。
提醒后不继续追问身体变化，也不借此追催白天未打卡的习惯。

最初只确认起床提前触发；后续用户于 2026-10-13 明确接受 R4：
当前明确准备睡觉可以提前触发当晚提醒，共用 21:30 的实例额度，不重复。

## 5. 身体状态记录

身体状态由用户随时主动报告，包括正面和负面的感受。例如：

- 「今天有点流鼻涕，也比较累。」
- 「昨晚开始右肩痛。」
- 「现在舒服多了。」
- 「今天精神很好。」

记录首先保留原话、发生时间与记录时间。用户提供时可保存部位、程度、持续时间或变化；
没有提供的信息保持未知，不强制填写整套表或打分。
补记「昨晚」「大概下午」等信息时保留时间的不确定性。

用户后来主动报告改善或加重时，可以关联原观察，但不主动发起追踪询问。
用户感受不能擅自转成诊断；旧系统的精力衰减公式不能充当实际身体状态证据。
到家、到学校或其他到达时间属于普通生活事件，必要时与身体记录关联，保持类型区别。

## 10. Hermes 基线与运行手册约束（2026-10-13 后续讨论）

用户明确要求基于现有 Hermes 和 honc 原有架构，一项一项讨论设计。
运行模型按用户所说的 Terra 级别能力来设计手册与工具，不依赖模型自行补全宽泛指令。
这里记录用户对运行能力的设计要求，不评定具体模型性能，也不更改模型配置。

### 10.1 现有结构和拟采用边界

仓库已有独立 honc Hermes profile、`SOUL.md`、四项业务 Skill 和
`honc-execution` MCP 语义工具；这些是本轮设计的基础。
现有 Skill 为 `honc-daily-execution`、`honc-tracing`、`honc-focus`、`honc-checkin`。
当前仓库角色与配置契约不能替代对真实运行配置的验收。

拟沿用 Hermes 的对话运行机制、profile／Skill 加载和工具调用入口，
通过扩展 honc profile、业务手册、语义工具和 honc 后端实现新能力。
具体提醒接入应先核实已安装 Hermes 的调度能力和权限边界，再设计适配；
不要凭空新增第二套模型运行循环或把开发工具权限交给日常 honc。

用户提供的 Notion [Agent CodeBook](https://app.notion.com/p/Agent-CodeBook-3dde1eb5ce57802489cae4082ff4b342)
是架构方法参照：持久状态、按需上下文、工具合同、机械约束、验证、追踪与交接。
框架／开发工具示例不构成替换现有 Hermes 架构的决定，也不授权并行 Agent 或部署。

### 10.2 手册必须具体且按场景组织

每项业务 Skill 的后续手册至少说明：

1. **触发与排除：**什么用户表达属于该场景；否定、询问、计划或引用为何不等于已发生事实。
2. **先读什么：**需要查询的状态／习惯、字段、来源与版本；缺失如何处理。
3. **逐步操作：**工具名称、调用顺序、必要参数与用户原话到字段的对应。
4. **缺信息分支：**哪些字段保持未知，哪些歧义必须简短补问；不得自己选一个对象。
5. **结果分支：**成功、已处理、部分成功、冲突、失败及结果未知时分别怎样处理和回复。
6. **重试与停止：**何时查询原回执，何时可重试，何时需要保留待处理项；不盲目重复写入。
7. **完整例子：**正常打卡、否定、补记、纠正、多意图及失败路径，包含实际工具输入输出。
8. **验证条件：**对记录与状态的期望，不能只检查回复中是否说了「已记录」。

手册详细程度与加载范围分开：入口说明保持简短，执行相关场景时加载对应步骤和例子。
详细手册不能增加每次对话的无关上下文；工具描述、参数约束与错误结果要与手册一致。
新增工具名称和字段在工具合同确定后填写，本轮不伪造已存在的接口。

### 10.3 降低运行模型的协调负担

来源身份、参数校验、实例归属、重复提交、版本冲突、提醒额度和持久保存由后端检查。
模型负责理解、选择合适语义操作并基于回执回复，不承担人工计数提醒或推测保存成功。
一条话包含多个事实时，工具返回各事实的结果；重试要能恢复已有结果而不重复记账。
批量还是分次调用及事务边界仍待工具设计时商量。

未来 Eval 应使用实际部署的模型配置走完整用户消息到工具回执的链路，
覆盖否定／询问不误打卡、同一消息不重复、部分成功不误报全成功，以及身体记录不引发追问。
不能仅用更强模型的演示或后端单元测试证明日常 honc 的对话能力已经通过。

当前继续按顺序讨论 Hermes／honc 职责边界、Skill 手册、工具合同、状态与提醒接入、验收。
本次补充仍是讨论与需求记录，不实施上述扩展。
