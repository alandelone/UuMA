## 1. 已确认的政策与默认值

| 规则 | 确认行为 | 默认值 |
| --- | --- | --- |
| R1 | 对应实例达标后取消尚未发出的提醒 | suppress_when_complete=true |
| R2 | 在窗口内仍可发送，窗口结束则过期且不追补 | missed_window_policy=expire；fixed_point_grace_minutes=30 |
| R3 | 同一时刻到期项合并，重要的列前面 | group_simultaneous=true |
| R4 | 明确当前提前准备睡觉，提前同一晚的提醒 | advance_bedtime_anchor=true |

起床默认 08:00，明确提前起床／开始当天计划可提前；睡前默认 21:30。
时区 Asia/Kuala_Lumpur。默认每实例一次；增加次数需要用户明确设置。
重要度不改变次数，不因未回复追加提醒；身体不主动追问变化。
这些默认可以通过受限业务设置显式修改，不能被模型推断、旧 Cron 或通用恢复覆盖。

## 2. R1：完成对应实例才抑制提醒

以 effective 事实和发生时习惯版本计算 instance.target_status，模型不决定该状态。
met 才抑制未发送的实例提醒；partial、unknown 或未记录不等于完成。
多次目标必须达到数值目标，不能仅因出现一条 completed 活动报告就算每日目标达标。
早餐完成只影响早餐实例；补昨天日记不影响今天；某一个习惯不抑制同组其它习惯。

抑制记录保存 SUPPRESSED 与原因 TARGET_MET，不伪造已提醒或扣掉打卡记录。
若配置显式允许多次提醒，完成后取消剩余尚未发出的次数，不撤销已经发生的发送。

发送前必须在业务原子领取／最终 dispatch 检查有效完成状态。
在进入不可逆的 SENDING 之前发生的有效完成应阻止发送；外部发送已经启动或 UNKNOWN
时不保证撤回消息，也不通过把 UNKNOWN 改为 SUPPRESSED 掩盖不确定性。
并发边界需要明确事务顺序及 fencing 证据，不能只在生成文案时检查一次。

## 3. R2：窗口边界与恢复

采用 start-inclusive/end-exclusive 区间，即 start <= now < end。
这属于工程端点约定；08:30 已离开 [08:00,08:30) 的默认单点窗口。

- 固定时间点：window_start=原计划 due_at，window_end=due_at+配置 grace。
- 固定时间窗口：使用配置的原 start／end，不额外附加 30 分钟。
- 在窗口内恢复：检查 R1、启用、额度、原发送状态后才能发送。
- 在窗口结束或之后恢复：标记 EXPIRED，记录原因与原窗口，不发送、不在夜间补催。
- 重启不能把 window_start 改成启动时间，否则会把过期提醒复活。
- 明确提前锚点：用实际锚点的调度时刻开启该实例提前发送窗口，使用同一 quota。
  保留原 fallback_due_at，不删除原计划的审计信息，也不在 fallback 时重复消费。
- grace 可配置；更新窗口只影响生效后的未发送计划，不能改写已发送和历史版本。
- 窗口跨午夜仍保留原计划所属的业务日，不因 now 的日期改变而换一个额度身份。

例子：15:00–16:00 的提醒在 15:20 可以发送，16:00 就过期；
08:29 的晨间默认计划仍有效，08:30 已过期；21:59 的睡前默认计划仍有效，22:00 过期。
这些例子只是验收输入，不是实时创建的提醒。

## 4. R3：合并同一时刻到期项

合并条件：同一有效 owner、同一绑定通知目标、同一原 due_at；
不同 owner／目标／时间点不得合并。不能只因为恢复时“都已经到期”就合成补催清单。
提前同一锚点触发的一组习惯采用该锚点同一调度时刻作为候选 group key。

先过滤已完成、已过期、停用、已送达、UNKNOWN 或额度用完的实例，再组消息。
按 high、normal、low 排序；同重要度使用稳定 habit_id／instance_id 顺序。
不会在同一消息随机重排造成重试摘要变化。

每条消息有 group_delivery_id，每项有稳定 reminder_id 与独立配额记录。
一条真实投递结果关联所有实际包含的项；不是每项再各发一条。
如果一次合并投递结果 UNKNOWN，所有包含项保持原未知状态，不拆开重发。
发送前被完成抑制的项可从尚未提交发送的 payload 中移除，保留修订／关联历史；
发送开始后不能悄悄改原 payload，重试使用已冻结内容与操作身份。

睡前日记项包含一次身体记录邀请；合并模板不能针对白天症状产生新的询问。
已完成的其它习惯不进入清单，白天遗漏且不同时到期的项也不进入清单。

## 5. R4：提前睡前锚点与默认时间共用额度

明确当前“准备睡了／准备睡觉”等真实用户消息可以触发 bedtime。
“明天早点睡”“想早点睡”“别人准备睡了”或引用消息不能触发当前 bedtime。
模糊表达不需要为了提醒而追问；保留原话或正常回复，只有明确语义才触发。

例如 20:45 用户明确准备睡觉：保存用户锚点，提前调度已启用的睡前实例，
默认 21:30 计划保留审计引用但不再发送同一实例。
21:30 已提醒后再报告准备睡觉：仍可记录锚点事实，不再次发送。
20:45 提前路径的投递 UNKNOWN 后，21:30 也不能通过 fallback 绕过去重。
锚点事实、计划、排队和实际投递结果分别保存，不把排队当作已送达或已入睡。

多次睡眠、跨日作息与其它情境不在这次四项确认中扩大；实现时以当前业务日
和已存在实例为作用域，未知归属保留待关联，不猜另一个睡眠周期来生成额外通知。

## 6. 共同处理顺序与状态

1. 获取可信 owner、配置版本与原计划实例。
2. 检查是否已送达、UNKNOWN、已有外部发送或有未释放的有效 claim。
3. 检查启用状态、允许的 trigger、原窗口及有效完成状态。
4. 检查已消耗／已预留的该实例额度；重要度只参与排序。
5. 原子领取并绑定 reminder/group/attempt 身份与 fencing token。
6. 冻结实际 payload，发送前执行最后有效性检查，复用 Hermes 投递路径。
7. 按真实投递结果持久保存状态；当前模型回复不作为发送证据。

第 2 步优先，避免对已有 UNKNOWN 通过过期或完成状态覆盖其实际历史。
记录事实与取消未发送计划可以同事务；外部投递无法与 SQLite 原子提交，
因此保留 outbox／稳定操作身份、明确 UNKNOWN 和可查询回执。
只在证明外部效果还没有发生时恢复同一逻辑发送；失去 fencing 的旧执行者不得再提交。
