# honc 详细实施计划：Graph 为主源的日常执行与追踪 Agent

## 1. 目标、架构与首版交付

本计划替换上一稿的实施口径，采用本轮已确认的选择：

- **任务主源：Yonc Graph。**
- **对话入口：Hermes 与独立 honc Telegram 身份。**
- **完成策略：明确的用户报告符合既定标准时，直接更新普通日常任务。**
- **界面：使用现有 Graph 与 Notion 页面，不新增 Dashboard。**
- **提醒：仅针对回合事件及需要处理的更新问题，不默认晨晚提醒。**

首版必须打通：

**读取 Graph 下一步 → 🛸 准备回合 → 🍅 执行 → 记录事实 → 核对完成 → 回写 Graph → 更新 Notion → 查回实际结果。**

| 系统 | 保留的权威职责 |
|---|---|
| Yonc Graph | 任务身份、结构、依赖、`done_when`、已接受的项目状态 |
| honc 执行服务 | 回合、执行事实、实际状态、习惯、完成依据、更新进度 |
| Notion | LIVE 今目和 DAILYSTATE 的展示与日记 |
| UuMA | honc 注册、Direct Run、运行结果及控制审计 |
| Hermes | 对话、平台身份、profile 隔离及消息传输 |

实现放在 UuMA 的 `uuma.honc` 模块中，通过独立 Hermes profile 和语义 MCP 工具提供能力。Graph 增加范围明确的执行接口；honc 不直接访问 Graph 数据库。

执行数据使用独立的 **`UUMA_DATA_DIR/honc/honc.db`**。Graph 数据库、`uuma.db`、`wisdom.db`、Hermes `state.db` 各自保留，不做跨库表连接。

首版包括手动记录、补记、纠正、基本习惯打卡、完整回合计时、Graph 完成回写、Notion 投影和事件提醒。旧 emoji 自动检测及 DayStyle 自动建议在首版验收后接入。

## 2. 数据模型与公开接口

### 2.1 honc 的持久记录

采用 SQLite、事务写入及版本化迁移。事实与纠正事件追加保存；当前状态表可以更新，但必须能从事件恢复。

| 记录 | 必须保存的内容 |
|---|---|
| `trusted_inputs` | 来源回执 ID、用户身份、入口、profile、会话／消息身份、原始报告、接收时间、来源摘要 |
| `task_snapshots` | Graph 数据库身份、节点 ID、所属主线、Graph 版本、任务状态、完整 `done_when`、相关内容摘要 |
| `rounds` | 用户、任务、果象、小笨事、Mode、计时预算、标准快照、当前状态、修订号 |
| `round_segments` | 每段开始／结束时间、中断原因、时间来源；暂停时间不计入执行时长 |
| `execution_events` | 事件类型、发生时间、记录时间、任务／回合／习惯引用、成果、Next、Blocker、State、Actual、修正引用 |
| `completion_assessments` | 核对粒度、标准快照、满足项、缺失项、依据、用户完成指令引用、核对结果 |
| `outbox` | 目标、操作身份、内容摘要、前置版本、处理状态、尝试次数、租约、错误、实际回执 |
| `projection_bindings` | 日记／回合／任务与 Notion 页面、受管容器、生成区块的稳定对应关系 |

习惯定义使用独立配置记录，包含稳定 ID、名称、字段类型、单位和可重复次数。每次打卡作为执行事件保存，不用一个布尔值覆盖全天所有发生。

统一约定：

- ID 由服务生成；显示用的 `T1` 等编号不作为身份。
- 时间保存 UTC 和原始时区；日期解释与日报使用 `Asia/Kuala_Lumpur`。
- 实际发生时间和补记时间分别保存。
- `Actual` 区分计时所得、用户报告和估计；未知时留空。
- 每个用户最多一个运行中的回合，Hermes 和 Telegram 共用这一约束。
- 报表从事件生成，不把模型总结新增成执行事实。

### 2.2 honc 的 MCP 工具

工具固定注册，所有写操作经过 honc 服务。模型不获得任意 HTTP、SQL、终端或 Graph 通用修改工具。

| 工具 | 输入与行为 |
|---|---|
| `honc_status` | 返回当前回合、数据源身份、连接状态、待核对及待更新项 |
| `honc_get_context` | 按项目／节点读取已接受的任务、标准、相关执行记录和当前 Next |
| `honc_record_execution` | 根据本轮来源回执记录进展、状态、成果或补记；允许暂时未关联任务 |
| `honc_control_round` | `prepare / start / pause / resume / end / cancel`，检查回合修订号 |
| `honc_check_habit` | 记录某个习惯的一次发生、数量或用户报告状态 |
| `honc_assess_completion` | 用保存的任务标准和执行依据生成核对结果 |
| `honc_apply_completion` | 提交满足条件的用户指令；返回 Graph 实际结果和后续同步状态 |
| `honc_correct_record` | 追加纠正，必要时准备或执行对应的反向更新 |
| `honc_get_report` | 查询某日／某周的 Done、Next、Blocker、投入及待处理项 |
| `honc_reconcile_updates` | 查回原请求并恢复待更新操作，不重新制造执行事实 |

写工具必须关联当前用户、当前 profile 和可信来源回执。其他会话或其他 profile 的回执不能被引用。

统一响应至少包含：

`record_id / round_id / assessment_status / graph_update_status / projection_status / receipt_refs / next_required_action`。

这样对话能准确表达「事实已记录」「任务已更新」「Notion 待同步」，不会用一句 Done 包含所有结果。

### 2.3 Yonc Graph 的最小扩展

当前 Agent 完成通道仍以频道判断权限，并拒绝 Agent DONE；需要增加用户决策来源，而不是把 honc 冒充成 UI。[现有完成限制](C:/Users/Alandelone/CodeSpace_Local/yonc_agent/graph_app/v2_service.py:470)

新增接口：

| 接口 | 用途 |
|---|---|
| `POST /api/v2/execution/action-decisions` | 接受可信用户指令对应的单个 ACTION 状态更新 |
| `GET /api/v2/execution/receipts/{operation_id}` | 查回原操作，解决超时后结果未知的问题 |
| `POST /api/v2/execution/focus-events` | 按稳定区间身份接收开始／结束事实，维护现有 Focus 记录及工时 |

`action-decisions` 只允许 `start / block / unblock / done / reopen`，不接受节点创建、删除、重排、日期、优先级或父子关系修改。

新增 Graph `ExecutionReceipt`，保存操作身份、语义内容摘要、节点、用户决策来源、执行者 honc、原状态、新状态、OperationBatch 和响应。回执与状态事件在同一 Graph 事务提交。

同时落实既有设计中的 `portfolio_role`：

- 仅根 GOAL 可拥有 `MAIN / SUPPORT / PARKED`。
- 最多一个 MAIN 和一个 SUPPORT。
- 在现有节点编辑界面配置，不新增页面。
- honc 只读取，不能自行改变角色。
- Main 未指定时，记录仍可使用；候选推荐等待用户指定，不自动选项目。

Graph 版本递增改为共享的原子版本检查；现有 UI、v1、v2 和 split 写入继续使用同一版本机制。新执行接口复用现有操作历史，不依赖尚未实现的完整 History／统一 WRITE 框架。

## 3. 核心行为与失败处理

### 3.1 可信用户输入

普通 MCP 调用不能证明「用户说过完成」。

在 Hermes 的真实本地输入入口、以及通过身份检查的 Telegram 接收入口，生成可信输入记录。现有 `pre_llm_call` 只传递该记录的引用及当前上下文；需要补充来源元数据时，仅扩展现有调用链，不增加通用核心工具。

Telegram 首版仅支持绑定用户的私聊：

- 校验真实发送者、目标 honc 身份和消息身份。
- 工具输出、网页内容、转述、定时提示、其他 Agent、机器人消息均不能成为完成授权。
- 本地输入区分真实用户输入与后台／委派调用。
- 服务凭据由运行进程持有，不进入模型上下文。
- 模型可以解释消息；不能新增用户未表达的完成指令。

会话恢复时读取持久执行状态，并将短上下文附在当前回合；不重建整段历史，也不在长会话中更换工具集或系统提示。

### 3.2 完成与纠正

自动回写普通 ACTION 必须同时满足：

1. 用户明确报告该任务完成。
2. 目标能唯一关联到 Graph 节点。
3. 节点已经接受、未归档，属于当前 Main／Support 范围。
4. 已有明确的 `done_when`，报告或成果依据满足该标准。
5. 当前任务内容与核对时的相关快照一致。
6. 不属于等待专门复核的 REVIEW 状态。

满足后直接提交，不再要求用户重复批准同一日常指令。

以下情况只记录事实并保留待处理项：

- 对象不明确，或只说「弄好了」但存在多个候选。
- 缺少任务标准。
- 只完成回合小成果，尚未达到原任务标准。
- 文件、测试或 Agent 结果存在，但用户未表示任务完成。
- 任务处于专门复核阶段，或者涉及里程碑／项目完成。

普通用户报告可作为依据，不强制截图。成果的领域审核仍由对应系统负责；Graph ACTION DONE 不代表科学结论、知识采用或工程安全审核通过。

用户纠正记录时：

- 追加修正事件，保留原报告。
- 若要撤回 honc 自己提交的完成状态，核对该节点仍对应原完成操作，再追加单节点反向更新。
- 节点已被别人修改时，保留纠正事实并报告冲突，不执行整批 undo，不影响父节点或其他任务。

### 3.3 回合和工时

回合状态固定为：

`PREPARED → RUNNING ↔ PAUSED → AWAITING_CHECK → CLOSED`

另支持 `CANCELLED`；异常恢复将运行区间标记为中断，等待用户恢复或补记。

默认 Focus 25 分钟，可指定 45 分钟或其他时长。计时到点关闭当前计时区间并进入 `AWAITING_CHECK`，只提醒留下成果、Next 和 Blocker，不自动完成任务或启动下一回合。

honc 负责新回合生命周期；Graph Focus 保留活动记录：

- 每个 honc 区间使用稳定身份同步 Graph。
- 暂停关闭一个区间，恢复创建下一个区间。
- 已关闭区间的工时只累计一次。
- 旧 Graph Focus start／stop 入口适配至同一回合服务，保留已有响应形式，避免并行启动两套计时。
- 跨午夜按实际区间拆分日报，仍属于同一回合。
- 服务中断后的未观察时间不自动计入；估计或补记单独标注。

这些计时表示区间投入，不宣称持续注意力检测。

### 3.4 Notion 更新

Graph 是工作任务真值。首版 Notion 工作任务展示采用单向投影；用户勾选 Notion 展示项不会直接变成 Graph DONE。

LIVE 今目：

- 保留现有果象卡和全部用户区域。
- 新建明确的 honc 受管容器，按区块 ID 更新。
- 展示本回合果象、小笨事、Mode、Timer、Done／Next／Blocker。
- 多种任务分类引用同一个 Graph 节点，完成只统计一次。

DAILYSTATE：

- 每日使用一个稳定绑定的记录位置。
- 保存成果、投入、状态、Next、Blocker 和待核对项。
- 原有习惯字段可按明确映射同步；不依靠名称猜测字段。
- 更正生成区时保留对应的修正历史和用户内容。

禁止调用旧的整页清空／重建入口；该路径会删除 LIVE 顶层区块。[旧 dashboard 写入入口](C:/Users/Alandelone/CodeSpace_Local/yonc_agent/dashboard.py:545)

Notion 没有可靠的跨请求事务保证，因此只写受管区域，写前比较已保存的远端摘要，写后读取核对。发现人工编辑差异时暂停覆盖并展示冲突。

### 3.5 更新队列与提醒

先提交 honc 执行事实，再分别处理 Graph 和 Notion：

- 操作身份保持稳定；同一身份改变语义内容返回冲突。
- Graph 响应未知时先查原回执，再决定重试。
- Graph 版本改变但相关任务内容未改变时，可以重新检查后提交原意图。
- 标准、状态或归属改变时停止自动更新，保留待核对。
- Graph 成功而 Notion 失败，返回「任务已更新，日记待同步」。

队列使用单个后台 runner、原子领取和租约。自动重试最多五次，间隔为 1、10、60、300、900 秒；超限转为需要处理，保留原操作身份。

提醒仅针对：

- 已开启回合到点。
- 用户主动中断的回合到达约定恢复点。
- 更新进入需要用户处理的失败或冲突。

同一事件去重；普通自动重试不逐次推送。通知通过服务发送到绑定用户，不向 honc 暴露任意收件人消息工具。Telegram 发送结果未知时不盲目重复发送，状态可在后续对话查询。

## 4. 实施顺序与每步完成条件

| 工作包 | 实施内容 | 完成条件 |
|---|---|---|
| **A：Graph 与来源基础** | 数据库身份校验；添加 portfolio role 和执行回执迁移；原子 Graph 版本检查；完成接口契约；梳理旧写入入口 | 已有数据保留；并发更新不丢版本；Agent 不能伪造用户完成；选定一个 Main ACTION 可读取标准 |
| **B：执行账本** | honc 存储、事件、快照、回合、补记、习惯、纠正、日报；实现读取和记录 MCP | 重启可恢复；同一消息不重复记账；未知时间不补造；修正历史完整 |
| **C：真实对话与 Graph 回写** | Hermes／Telegram 输入来源；独立 profile；用户指令核对；ACTION 更新及原回执查询 | 两入口共享记录；明确完成直接生效；否定、转述、歧义及其他 Agent 结果不会误完成 |
| **D：回合与事件提醒** | 开始、暂停、恢复、结束、到点查成果；Graph Focus 适配；后台 runner 和定向通知 | 单一活动回合；暂停不计时；重试不双计；到点只结束回合，不自动 DONE |
| **E：Notion 与首版验收** | LIVE／DAILYSTATE 受管区域；字段映射；同步队列、查回和冲突；Yonc 只读摘要 | 果象卡完整；Graph 和日记结果分别可查；离线恢复不重复追加；完整闭环通过 |
| **F：旧能力迁移与扩展** | 导入已关闭旧 Focus 历史；接入有稳定映射的 emoji 观察；DayStyle 模板、实际状态对照；停用重复写入 | 未映射历史明确保留；预计状态不成为实际事实；同一来源只有一个写入负责人 |

**A–E 构成首版发布要求，F 为后续增量。**

profile 固定为 `honc`，配置两个 MCP：受限 `uuma-worker` 和 `honc-execution`。新增身份必须同步注册到 Worker 身份校验、Agent registry、技能允许列表、部署器和 guard。

配置四项技能：

- `honc-daily-execution`
- `honc-tracing`
- `honc-focus`
- `honc-checkin`

honc 只拥有自己的运行报告和执行领域工具。Yonc 的角色资料增加 honc 边界，并通过只读摘要接口读取真实成果、投入及重复 Blocker；摘要读取不派发新 Agent 任务。

Hermes 和 Telegram 使用同一 gateway 的 profile multiplexing。honc 使用独立 Telegram 身份；模型和供应端沿用现有 Yonc 配置，不在此次建设中换模型。

## 5. 测试、发布与默认值

### 必须通过的测试

| 测试组 | 核心场景 |
|---|---|
| 输入与权限 | 正确用户／错误用户、私聊／群聊、其他 profile、后台任务、转述、引用和伪造来源 |
| 日常记录 | 昨日补记、未知 Actual、多次同类习惯、重复消息、未关联任务、追加纠正 |
| 完成核对 | 未完成、部分完成、完整完成、缺少标准、标准改变、REVIEW、父节点和计划外任务 |
| Graph 写入 | 同操作重试、改变内容复用 ID、并发版本冲突、提交后响应丢失、撤回时人工改动 |
| 回合与工时 | 双入口同时启动、暂停恢复、到点未达标、跨午夜、异常重启、重复同步 |
| Notion | 果象卡保留、多分类同一任务、分页区块、写入超时、人工编辑冲突、纠正投影 |
| profile 隔离 | 两个临时 Hermes home 执行 A→B→A；来源、工具、缓存上下文及记录不串用 |
| 兼容性 | 原 Graph UI、v1／v2、split 提交、操作历史、已有 Agent 权限及身份校验保持有效 |

验收先使用临时数据库、两个隔离 profile 和专用 Notion 测试页面；随后在一个 Main 项目及少量习惯上试用。真实验收保留输入来源、完成依据、Graph 回执、Notion 查回结果和失败恢复记录。

发布前备份 Graph 数据库、现有 profile 配置及旧 ID 映射。迁移需测试已有数据库、失败恢复和重复启动；不能以新空数据库替代既有数据。

切换时先停用已接入范围内的旧 dashboard／完成写入，再启用 honc 写入。其他范围继续保留旧流程。回滚停用 honc 对外更新和提醒，保留全部执行记录；恢复旧入口前核对受管范围。已经接受的 Graph 结果通过明确反向操作处理，不通过恢复旧数据库抹除。

部署诊断应能显示数据库身份、最近 runner 心跳、当前回合、队列积压、冲突和最近失败；诊断不主动刷屏。

固定默认值：

- 一位绑定用户，一个 Main，至多一个 Support，一个运行中的回合。
- Focus 默认 25 分钟；没有自动晨晚计划。
- 普通 ACTION 用户报告可完成；项目、里程碑和专门复核仍走原流程。
- 工作任务以 Graph 为准；习惯和执行事实以 honc 账本为准。
- 没有记录显示「未记录」；没有可靠状态显示「未知」。
- DayStyle 只是预计情境；没有设备监视、浏览历史采集或注意力推断。
- 不引入 `⁉️` 分级，不自动调整项目树和优先级。
- 用户 ID、Telegram 凭据、Graph 数据库身份、Main／Support 节点和 Notion 目标在部署时配置；程序不得猜测或自行创建替代项目数据库。
