# honc 后端第一批成果与可评论内容

日期：2026-10-13。状态：后端组件已实现并通过隔离测试；现用 Hermes Agent 尚未接入。
没有前端，也没有新增真实通知、修改现用习惯、迁移用户数据或推进项目审核关卡。

## 这批已经做到的

| 内容 | 实际完成范围 |
| --- | --- |
| 习惯管理 | 创建、修改、暂停、恢复、退役；保存每个版本，修改时检查旧版本是否仍有效 |
| 习惯打卡 | 布尔、次数、数量、时长、文本；支持日期补记；一批事实整体保存，单位不明确时返回问题 |
| 身体记录 | 保存用户主动说出的好／不舒服的状态；未说的部位、程度、分数保留未知；不从症状推断诊断或变化 |
| 日记 | 保存用户原文和明确日期；可关联同用户记录；暂不自动生成日记习惯打卡 |
| 修正与撤销 | 新增版本，保留旧记录；撤销后从有效视图移除，审核历史仍可看到 |
| 设置 | 可修改起床／睡前时间、默认次数、重要度及支持的提醒策略；默认 08:00、21:30、一次 |
| 重试保护 | 同一消息的同一写入返回原回执；内容变了返回冲突；同时提交也只保存一份 |
| 工具接口 | 准备了 9 个语义工具的注册函数，供原有 honc MCP 接入；没有启动另一套 Agent |
| 提醒规则 | 完成纯规则判断：已完成取消未发送提醒、窗口过期、不因重要度加次数、同时间分组、明确早起／早睡提前同一实例 |

用户身份和消息引用由可信入口绑定，工具参数不能自称用户、收件人或消息来源。
可信入口默认不发写入授权；只有核实用户允许的操作才产生对应引用。
数据库变更只增加 honc.db 内的独立生活表，旧执行表和工作回合不受这些操作改变。

## 三个值得评论的使用例子

以下是产品行为示例，尚未做真实模型对话验收：

1. 说「流鼻涕，也有点累」：保存这两个原始感受，其他信息留空；不接着问身体变化。
2. 说「昨天运动二十分钟」：找到已存在的运动习惯，按分钟和昨天记录；不补造准确时间，也不结束当前工作回合。
3. 说「刚才记错了，改成三十分钟」：明确原记录后追加修正；仍能查到原来的二十分钟。

晚上邀请记录日记／今天身体状态，属于相应习惯的一次提醒。不会把下午没打卡的习惯
集中到晚上再次催补。这个方向已经确认，不需要重新批准 R1–R4。

## 尚未完成的连接

- Hermes 真实用户消息入口：核实 sender、profile、session、message_id，并给工具提供当前消息的绑定服务。
- 原习惯迁移：逐项保留名称、单位、目标和旧记录，审核旧 Cron 条目与习惯实例的关系。
- 持久提醒实例与发送回执：原子保留次数、关联真实投递状态；纯规则 ELIGIBLE 还不是发送成功。
- 打卡与对应提醒实例、日记与日记习惯的绑定；当前拒绝未经核实的 instance_id。
- 起床／睡前锚点的持久事实、调度和真实消息入口认证；当前只完成规则层的提前判断。
- 历史筛选与稳定游标、明确停用习惯的专用历史补记路径、撤销后的显式恢复合同。
- 新会话边界注册工具、详细 Skill 上线及真实普通模型场景验收。

当前历史接口支持明确记录或日期范围、effective／audit、每页最多 100 条。
分页 offset 是暂定接口，不能当长期稳定游标。当前每条真实消息每个领域只有一个原子写入授权，
习惯打卡可以包含 1–8 项；多次独立配置同一领域需要后续的可信事实授权拆分。
