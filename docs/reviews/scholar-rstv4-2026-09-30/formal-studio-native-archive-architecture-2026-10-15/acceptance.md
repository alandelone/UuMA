# Studio 原生归档／恢复与当前构建架构核验

本批新增 RE-10 的 A206 原生归档／恢复证据，以及 ST-01 当前构建的静态架构证据。全部 118 条及最终同源 11 组贯通仍未完成。本报告没有批准科学内容、外部投稿／接收或项目 gate。

## A206 原生操作与持久化核对

官方 Windows Computer Use 在真实 Chrome、当前源码和既有真实编译前端上完成了 24 次观察。先点击“开始修改意见 A206”，实际显示“正在回应”和 A206 活动关联；返回 Revision 后点击“移入已删除 A206”。服务返回 200 后，页面明确恢复“普通编辑／后续修改不关联审稿意见”，当前意见卡消失；修改历史保留 A206 并注明归档。

切入“已删除”后，原意见、作者决定和完整回复可读且不可编辑，四条修改链接保留。实际打开“A206 的核对历史”，看到原两条作者核对记录、固定成文 v5、当时完整回复及原定位。没有重新核对旧回复，没有产生新的核对记录。随后点击“恢复意见 A206”，服务返回 200，归档列表为空；切回当前意见并实际点击“重新读取意见与轮次”，同一 ID／编号 A206 和完整原回复仍在。恢复后仍为普通编辑，未自动激活旧关联；页面提示原核对已过期、需要重新核对。

数据库逐表核对证明：

- 两次原生业务请求仅为同一评论的 DELETE（软归档）和 POST restore，均为 200；没有用接口请求冒充点击。
- 仅 review_comments 与 studio_comment_response_state 两表发生变化，其余 108 表及所有其他意见精确一致。归档只改变该条 archived_at／updated_at；恢复后相较最初仅 updated_at 不同，response revision 按 6→7→8 推进。
- 原 554 字回复、原意见、决定理由、两条核对历史及四条修改关联精确保留。没有把恢复理解为重新认可旧回复。
- 作者结构 revision 62、工作流 revision 6、当前生成 v5、第二轮固定 v3／r10 基线都没有变化。三个 revision 不能混用。
- 同一隔离副本及原始根目录保留；当前 311 份后端文件、91 份前端产品文件、76 份编译文件、原始 109 表和外部 25 产物摘要均保持。没有模型、GPU、生成或 worker 执行。

这些内容来自明示的软件验收稿件；配置中的作者核对标签及软件操作不代表真人科学批准。其它撤销／历史组合和最终贯通仍须各自证据。

## 当前构建的 ST-01 架构边界

完整比较当前前端 91 文件与实际编译目录中的对应源文件，以及 76 个冻结编译文件；解析 90 个 TS／TSX 文件和一个共用研究讨论控制器，共 91 个语法树。共 95 个不同运行时导入，没有直接数据库驱动或模型厂商 SDK 导入。审查全部网络调用位置和环境变量引用，浏览器稿件请求集中在 studio-api 的 RSTV4 API 地址，固定文件下载走同源文件代理。代理只接受规定的本地 API 地址和固定资源路径，不接受带用户名／密码地址，不追随跳转。

对 dist/client 的全部 23 个资源逐字节检查，未发现当前配置的 gateway key、模型入口、模型凭据环境变量名或列明的数据库连接／私钥标记。模型凭据只在 Python gateway 服务端读取。该检查针对已冻结的本地构建及已列明的可执行入口，不是任意第三方代码的全面安全认证。

权威保存路径有正面源码依据：浏览器提交 manuscript ID、base_revision 和 operation_id → FastAPI → StudioService.save_document 的事务、版本冲突校验及追加操作／修改记录。浏览器 IndexedDB 名称虽包含 studio，但其用途为 pending-saves 草稿发件箱；localStorage 保存草稿和界面状态，不是直接连接 RSTV4 catalog.db。没有移除离线保存功能来获得通过。

这次核验没有重跑完整测试。既有同源码 1130 项回归及 12 套 Catalog JS／Ruff 结果继续保留；静态架构检查与真实跨工作面最终贯通分别计证。

## 中断、失败及剩余范围

首次审计在完整快照重复 JSON 编码时发生 MemoryError；此前还出现 Windows 提交内存／分页文件不足，使会话包装器在命令执行前失败。保留失败工具，修为直接比较完整快照并只规范化 schema 的 tuple/list 表示，所有 110 表、所有行、所有字段及历史断言不变；未重跑两次已完成原生操作。架构扫描首版把整个 IIFE 的源码当作调用名称而误报，第二版按 AST 的实际调用表达式类别识别，保留首版工具，没有修改产品或放宽检查范围。

中断后，原 v6 服务 PID 均已不存在，原因未确定；新建服务前先独立确认原身份消失。旧前端端口 63377 已进入 Windows 的 63290–63389 保留范围，准备 v7 因 WinError 10013 中止，没有启动服务。后续仅由操作系统 bind(0) 分配前端 61614，后端仍为 8877；复用同一副本、同一编译前端，无新复制、构建、迁移或数据重置。启动与退出前后全部 110 表及非 sidecar 文件均与 A206 已恢复快照一致，零新增业务请求；自有前端、后端及控制台子进程已精确停止，8877／61614 已释放。没有改变系统端口／防火墙／权限配置，也没有停止其他应用。

后来新提供的官方 Browser 插件按目标 URL 选择了内置浏览器。首次页面遇到已停止的旧端口；当前错误页采用 data: URL，浏览器策略随后拒绝从该页导航或关闭该页。按其文档查询了恢复说明，关闭错误页也同样被拒绝，没有切换其他自动化机制绕过。新端口上的 Studio 业务动作仍为 0。请求用户手动关闭本轮错误页；保留用户要求保留的 8891 页。EXPLAINED_NO_CHANGE、WF09／10 和最终 11 组贯通尚未执行。

用户已同意服务恢复后为原 QuickRead 增加 30 分钟；这份授权保留。但现有程序最后一次真实访问仍为 gateway 403／1010，未获新的服务恢复通知前不重试、不改变签名／代理／凭据。预算未增加，QuickRead 未执行，GPU 第 6 次成功任务没有重跑。
