# Lab bot 电商采购、订单提取与库存协作：MCP 需求

**版本：** 0.5，技术契约修订，整行 self/others 已由用户确认  
**更新时间：** 2026-09-27  
**目标环境：** 用户自己的 laptop、现有浏览器登录资料、Lab bot MCP、Excel 审阅文件  
**核心原则：** 订单是采购证据；实物到货、核对并明确确认后，才增加可用库存。

## 1. 目标与当前优先级

本项目让 Lab bot 协助用户从电商网站收集**自己已经购买的订单与商品信息**，形成可审阅的采购记录，并在样品到货后与标准元件、批次和库存关联。用户仍会亲自使用自己的电商账号和浏览器。

**当前第一个要实现的能力是订单信息提取：** 在用户已登录的订单列表中，读取订单及订单行；列表信息不足时，在用户允许的范围内只读打开订单详情，取得商品、规格、购买数量、价格、状态等信息；把结果交给用户核对。提取成功不等于自动入库。

后续能力包括订单去重、订单用途与归属筛选、标准元件匹配、包装换算、到货验收、库存写入，以及根据需求比较平台报价。按本轮补充，网页加购纳入独立交付步骤：先采价和比较，再由用户选定方案并确认加购内容，最后核对购物车结果。下单、付款和平台确认收货由用户完成。本轮交付需求与实施计划，并做少量只读可行性核验；不代表已开始批量提取或实际加购。

## 2. 使用方式与平台范围

- 用户通过聊天发起提取、审阅、比价和收货操作；逐行核对或修改时使用 Excel。
- 优先研究如何使用用户**现有的 Chrome profile 和已登录会话**。可评估浏览器扩展与本地 MCP 服务协作，使用户在同一浏览器中继续正常操作。
- 当前试点为用户提供的淘宝、拼多多和 Shopee 马来西亚三个已打开标签页；Lazada 保留为后续范围。每个平台分别验证账号角色、地区、网页结构、可访问的订单页及许可条件；不得把一个平台的能力推断到其他平台。
- 若浏览器读取或平台接口不可用，用户提供的订单文件、发票、截图、商品链接或手工资料仍是第一阶段的有效输入。
- 仅处理用户授权访问的本人账号、订单和商品资料。平台网页或接口中的可用性均需在用户实际账号上验证。

## 3. 浏览器接入需求与待验证方案

> **已确定路线：** 自建 Chrome 扩展（Manifest V3）+ Native Messaging + Python 桥接进程（spawn 独立 `uuma.mcp_worker` 实例）。扩展采用厚扩展架构，每个平台一个 content script 模块（`shopee.js`、`taobao.js`、`pdd.js`），共享框架（`core.js`）处理生命周期。Unpacked 开发模式加载，不发布至 Chrome Web Store。

用户希望复用自己的 Chrome profile，减少重复登录，并能随时接管浏览器。**主路线为通过浏览器扩展和 Browser Control MCP 操作实际网页；不依赖电商平台 API，不调用未公开接口来替代页面操作。** “不用 API”指不对接电商数据接口，扩展和 MCP 之间仍需要正常的软件通信。已选择自建厚扩展，以下保留连接方案背景，并非承诺所有网站均可控制：

1. **浏览器扩展读取当前已登录页面。** 扩展在用户明确触发的目标网站订单页读取可见列表、按需读取详情，并把结构化结果交给本地 MCP 服务。优先使用当前登录会话完成读取，不以导出原始 cookies 为默认前提。
2. **浏览器自动化附着现有会话。** 不作为首选：Chrome 136 起，针对默认用户数据目录的远程调试开关不再生效。若考虑其他连接方式，须先验证它能可靠使用用户实际 profile、保持用户可见和可接管，并避免占用或破坏正在使用的 profile。
3. **平台接口。** 仅保留历史研究背景，不作为当前实施依赖；未来用户改变路线时另行评估。
4. **资料导入。** 作为各平台都可使用的保底路径。

如某一实现确实需要会话凭据，必须先证明用途和权限边界，采用最小权限、短期使用及本机安全存储；不得将 cookies、访问令牌或密码写入 Excel、日志、订单数据库或聊天摘要。需要记录的是订单来源和提取时间，不是会话密钥。

浏览器提取必须可由用户启动与停止，并能在登录失效、验证码、页面变化、网络错误时暂停，清楚报告已提取范围和未完成范围。不得绕过验证码或访问控制。第一阶段只读，不点击付款、确认收货、退款、删除订单、加购等会改变平台状态的操作。若采用扩展，权限只覆盖选定站点；扩展与本地 MCP 的通信需要验证消息来源并限制可调用操作。

## 4. 订单提取与核对流程

1. 用户指定平台、本人账号、订单页、时间范围或订单号，或提供订单资料。
2. Lab bot 记录来源、账号的本地标识、提取时间和范围；读取订单列表及必要的详情。对分页、懒加载、重复显示和中断续跑保留可追溯状态。
3. 订单按 `(platform, account_id, order_id)` 隔离。优先用平台行 ID，否则按商品和规范化 SKU 建立候选关联并分配稳定 `line_id`；同键碰撞保留所有来源并待核对，不合并覆盖。Excel 行号或文件 hash 不作业务身份。重复同步追加变化证据、补齐未完成详情并保留用户修订；已见订单不永久跳过。
4. 提取的原始字段与 Lab bot 推断字段分开保存。缺失、矛盾或不确定的字段保持“待核对”，不凭猜测补齐。
5. Lab bot 生成“订单待核对”Excel，标出商品标题、SKU、型号、规格、包装单位、购买数量、金额、退款、取消和部分到货等问题。
6. 用户修改 Excel，并在聊天中指出审阅的文件版本。Lab bot 汇总修改和待解决项，订单可进入“待收货”；此时**不增加库存**。
7. 包裹到达后，用户核对实收数量、品质、批次和库位。Lab bot 在聊天中列明拟写入的每条库存记录，取得明确确认后通过受治理的 MCP 收货操作写入，并关联订单行与收货批次。

平台显示“已签收”或“交易完成”不能代替实验室的实物验收。元件身份或包装换算未确定的行不得直接入库。

## 5. 每条订单行需要的数据

| 类别 | 字段与要求 |
| --- | --- |
| 来源 | 平台、账号本地标识、订单页或文件来源、来源链接或文件指纹、提取时间、提取方式、原始记录指纹 |
| 订单 | 平台订单号、下单时间、订单状态、币种、订单实付金额、优惠、运费、税费、退款与取消信息；无法准确分摊到订单行的金额保留在订单层 |
| 订单行 | 稳定行 ID、平台商品 ID、SKU/规格选项、商品标题、商品链接、店铺、购买单位、购买数量、单价、行金额、订单行状态 |
| 元件核对 | 厂牌、精确型号 MPN、封装、额定值、接口/版本、eSchematic 标准元件候选、匹配依据、置信程度、审核结论 |
| 数量换算 | 每购买单位包含的库存基础单位数量、预计基础单位数量、换算依据、不确定原因 |
| 所有权与分类 | ownership 整行只选 self/others，不支持用途数量拆分；未审阅时不设置 ownership，以 review_status 表示待审阅。category 为 electronics/consumable/tool/other；AI 建议、用户确认和 review_status 分开。新采集 others 行明细仅留本机 JSON/Excel，不进入 lab.db。 |
| 收货 | 预计数量、累计已收、此次实收、此次不良、批次、状态、库位、验收时间、验收备注、收货事件 ID |

同一订单可能包含多个商品、套装、多个装、赠品、拆单、部分发货、取消或退款。原始页面只提供订单总额时，不要伪造准确的行金额。订单状态变化应形成可追溯更新，而非覆盖掉既有收货事实。

## 6. 商品与库存规则

- 所有新提取订单行默认“用途待分类”。AI 可以建议用途，但不能因为商品看起来像电子元件就自动认定属于实验室。只有用户确认整行 self、电子类并明确用于实验室的订单行进入收货候选。
- **用户已确认（2026-09-27）：** 整行 self/others，不支持用途数量拆分，替代原实验室/个人/代购数量分配规则。不建立用途子行或分配比例。混合用途行保持待核对，不得抽取其中部分数量作为 self 入库；部分到货仍可分批验收，但所有批次沿用整行 ownership。
- 已排除或已分类记录再次同步时保留用户结论，不反复提示或自动重新纳入。退款、数量变化或用途调整产生差异待核对；已有收货时，改用途不能静默删除或改写库存流水。历史已存行改为 others 时追加排除修订，不清除历史；这不允许继续写入新的代购明细。
- 标准元件匹配优先使用厂牌和精确 MPN，再核对封装、额定值、接口、版本和其他关键规格。平台商品 ID 与 SKU 仅用于追踪购买对象，不能代替标准元件 ID。
- 套装、组合商品和多件装须分别记录“购买单位”和“库存基础单位”。换算不明确时保持待核对。
- 标准元件新增或等效替代须工程审核。身份不明的样品可保留采购证据，但不计入该标准元件的可用库存。
- “已订”“在途”“待收货”“已验收”“退货/报废”状态分别记录。未验收的货物不算可用库存。
- 收货写入必须新增 confirmation_id 和服务端审批验证；现有 inventory_receive 尚未满足本契约。同一订单行可多次部分收货，同一确认键与相同 payload 重放返回原事件，不同 payload 拒绝；确认记录与库存事件在 lab.db 同一事务写入。
- 用户必须明确确认将写入的元件、数量、状态、批次和库位；Excel 中填写“确认”仅是审阅意见。

## 7. 比价与购买建议（阶段 2）

用户在聊天中提出元件、规格、数量、交货要求或选择 BOM 缺料。Lab bot 查询可用库存和属于实验室的有效已订数量，确定需采购量，通过指定浏览器搜索、打开商品页、选择规格并读取报价，或处理用户提供的资料，只比较规格相同或已批准等效的商品。采价阶段不为了查看价格而隐式执行加购；只有结算阶段可见的费用标为待确认。

每项报价保留平台、店铺、商品链接、原币价格、购买数量、最低购买量、整包/阶梯价、确定可用优惠、境内运费、跨境或集运运费、税费及手续费、汇率来源与时间、报价采集时间、风险及未知费用。以**同一规格、同一需求数量、同一马来西亚收货地点**计算预计 MYR 总到手价：

> 商品金额 − 确定可用的优惠 ＋ 境内运费 ＋ 跨境/集运运费 ＋ 已知税费和手续费，再按记录的汇率折算。

未知费用显示“待确认”或区间，不能按零计算。比较应考虑拼团条件、满减、运费券和合单运费。用户审阅“比价清单”Excel 后，Lab bot 生成内部采购清单及链接；用户在平台自行购买，并在购买前重新核价。

### 7.1 独立的网页加购步骤

用户选定方案后，展示平台账号、店铺、商品链接、确切 SKU、购买单位、数量、当前价格与可接受价格范围。明确确认后才执行指定加购。商品规格、账号或价格越界时暂停并重新展示差异。

加购前读取该 SKU 在购物车中的现有数量，并明确本次是“增加 N 件”还是“调整到总共 N 件”，默认采用已展示并确认的语义。每次操作记录请求 ID、原数量、目标数量及结果。点击后必须核对购物车对应 SKU 和数量；超时或结果不明时先检查实际状态，不能盲目重试。不得为了测试而清空或修改无关购物车商品。若页面仅提供“立即购买”等无法独立加购的路径，报告该 SKU 不支持当前加购步骤。

## 8. Excel 审阅文件

每个文件显示文件版本、生成时间、来源摘要、币种、汇率时间和未解决项目数。每行有稳定 ID，排序、筛选和重新导入后仍能映射原记录。原始平台字段、计算结果、推断与用户可编辑列要清楚区分。

| 工作表 | 主要内容 | 用户填写内容 |
| --- | --- | --- |
| 说明与摘要 | 文件版本、来源、币种、汇率时间、未解决项 | 总体备注 |
| 订单待核对 | 平台、订单与订单行、商品、SKU、数量、包装换算、金额、元件候选、退款状态 | 整行 ownership（self/others）、排除原因、正确元件、包装含量、备注、接受或退回核对 |
| 比价清单 | 平台、店铺、链接、规格、数量、价格、优惠、各段运费、税费、汇率、MYR 总额、风险 | 选择、排除、备注 |
| 收货确认 | 订单行、预计数量、累计已收、批次、状态、库位 | 此次实收、不良数量、库位、验收备注 |

Excel 是审阅文件，不是正式库存账本。用户确认前，MCP 必须在聊天中展示拟写入记录。

新格式包含 schema_version、workbook_id、export_id、line_id、base_evidence_version、base_review_version。新增 commerce_preview_review_workbook / commerce_commit_review 处理四表格式；旧 inventory_preview_or_import_order_workbook 仅保留淘宝格式兼容。排序不改变身份；旧版本、篡改原始字段和重复 ID 必须报告冲突。审阅提交不写库存，收货另需具体预览和用户确认。

## 9. MCP 职责与建议能力边界

| 能力 | 用途 | 写入边界 |
| --- | --- | --- |
| 来源与会话状态 | 查询各平台连接状态、当前账号可用性及授权范围 | 不输出凭据 |
| 订单提取 | 从已授权订单页或用户资料取得订单及订单行，返回来源与覆盖范围 | 只读平台；采购证据可写入本地数据库 |
| 订单核对 | 去重、匹配元件候选、检查包装与金额、生成 Excel | 用户审阅前不写库存 |
| 比价 | 采集报价、计算总到手价、生成 Excel 与内部采购清单 | 不加购、不下单 |
| 加购预览与执行 | 展示选定 SKU 与数量；明确确认后操作并核对购物车 | 不提交订单或付款；结果不明先核查 |
| 收货预览 | 列出将新增的批次与库存流水，检查未解决项及幂等键 | 预览不增加库存 |
| 确认收货 | 用户在聊天中明确确认后记录收货事件与库存流水 | 仅此操作增加已验收库存 |
| 浏览器提取 | browser_start_extraction 派发持久任务；native worker 领取并提交批次 | 控制在 uuma.db；原始批次在本机归档；lab.db 只写允许的采购证据；持久回执后推进检查点 |
| 浏览器采价 | browser_search_products 派发只读搜索任务，browser_snapshot_offer 提交报价 | 平台只读；本地任务/报价有审计记录，不把结果登记误当成页面操作 |
| 浏览器加购 | 具体预览获确认后 browser_add_to_cart 派发；browser_check_cart 核验实际状态 | 检查购物车对平台只读，但可写本地快照；结果不明不重复点击 |

> **拟弃用工具：** 新 browser_* 尚未实现。只有对应功能通过验收后才切换 procurement_check_crawler_status / procurement_auto_search_and_evaluate；保留旧实现与回退。订单提取通过不代表搜索或 1688 已替代。

Native 模式 worker 只允许领取任务、续租、提交批次和状态查询，不能调用库存写入。身份环境变量不构成用户确认；任务范围、租约和业务批准均由服务端校验。所有原始批次先持久落盘，以唯一 batch_id/hash 处理重放，跨归档、lab.db、uuma.db 的部分成功通过回执恢复，不能声称跨库原子事务。

MCP 应返回结构化结果、来源、时间、错误与未完成范围，供聊天解释和 Excel 审阅。采购证据、标准元件、库存账本分别由既有受治理系统负责；具体 MCP 工具名称与 `lab.db` 表结构须对照现有实现确定。

## 10. 平台连接状态

浏览器路线逐平台显示：**目标 profile 已识别、标签页已识别、登录状态已验证、工具允许访问、列表读取通过、详情读取通过、分页/续跑通过、加购验证通过**；每项分别记录证据、时间和失败原因，未测不能写成通过。API 历史研究另用“文档存在、应用获批、本人账号已授权、只读样本测试通过”，不将 API 准入作为网页读取的前提。

## 11. 分阶段交付与验收

| 阶段 | 交付 | 验收标准 |
