# Agent 研究工具与可解释的持续研究

状态：2026-10-02 用户要求的架构更新；运行实现差距见末节。

本契约适用于 UuMA 中获准使用研究工具的 Agent，首先落实于 Wisdom-Oldman。
它补充 [系统架构](system-architecture.md) 和
[Wisdom 需求](../agents/wisdom-oldman.md)。较早记录中将 ChatGPT 描述为另一个研究者、
或将“没有新来源”作为自动暂停条件的表述，由本契约替代。

## 1. 工作归属与架构层次

Wisdom 拥有主题、问题、研究目标、知识判断和文字成果。ChatGPT 是 Wisdom 可派工的工具；
工具返回建议、搜索线索或研究报告，Wisdom 负责核查、综合和接续研究。
工具调用不创建另一位 Agent、不转移主题所有权，也不赋予知识批准权限。

```text
用户对话 / 已有主题与问题
  -> 意图与上下文解析
  -> 读取已有答案、研究状态及值得研究的缺口
  -> Wisdom 决定下一步及适合的工具
  -> 工具适配器：提交 -> 保存请求 -> 等待 / 接续 -> 收回结果
  -> 读取原始来源、比较条件、识别冲突、形成候选知识
  -> 发布主题文字文档与必要 digest
  -> 复评缺口并继续
```

职责分层：

| 层 | 职责 |
| --- | --- |
| SOUL | 工作归属、持续研究、诚实报告状态、权限边界 |
| Skill | 工具选用方法、任务包装、结果判断、证据整理 |
| 能力目录 | 已安装、已授权、当前可用的工具、模式及额度 |
| Planner | 按缺口选择问题、查询方式、工具和后续行动 |
| Executor / Adapter | 实际调用、幂等提交、状态检查、报告回收、失败分类 |
| Orbit | 持久任务、预算、租约、恢复、暂停及停止 |
| Knowledge / Document | 证据、候选、关系、文字版本和固定链接 |
| Conversation / Notification | 回答用户、解释状态、发送重要变化 |

仅修改 SOUL 或配置模式不能证明后台已经完成工具调度。Planner 的选择必须由 Executor
产生可核查的请求和结果记录。

## 2. 每个工具的能力契约

以后增加来源时，接入同一能力目录与适配器，避免把供应商名称和固定顺序写死在研究循环。
能力目录须包含：

- 稳定工具标识、说明、调用入口和操作指引位置。
- 支持的工作：解释与检索策划、来源发现、资料读取、跨来源研究等。
- 适用问题、所需输入、返回内容和来源位置的格式。
- 允许使用的 Agent、已授权范围和需要用户处理的边界。
- 启用状态、可用性、最后检查时间；未知与不可用分别表示。
- 配额、速率、计费限制、预计等待方式，以及恢复、接续和取消能力。

发现新工具不等于获得使用权限。已有权限范围内的工具可由 Wisdom 自主选择；新增账户、
付费额度、范围扩张、登录或验证问题仍按原有授权边界处理。
其他 Agent 的权限保持不变，尤其不得替 Scholar 或 Yonc 绕过 ChatGPT 排除规则。

工具结果使用统一语义区分：成功、有待处理的请求、无匹配结果、暂时失败、额度耗尽、
需要输入和需要人工恢复。不能把这些情况全部转换成空来源列表。

## 3. ChatGPT 的使用方法

| 模式 | Wisdom 可以交给它的工作 | 结果如何使用 |
| --- | --- | --- |
| `chat` | 拆解资料缺口、解释术语、提出别名和关键词、分析搜索失败、建议出处或比较条件 | 作为待核查线索和暂定解释；不直接成为事实证据 |
| `search` | 沿明确问题寻找公开资料、原始出处及引用线索 | 读取实际来源，保留定位及适用条件 |
| `deep_research` | 对值得深入的缺口展开多来源调查、比较、冲突整理和详细报告 | 保存完整报告、来源和接续记录，再核查重要结论 |

这三个模式可服务同一旧主题。Wisdom 按问题价值和当前缺口选择模式，不要求用户逐次
指定“去用 ChatGPT”。研究预算的 `DEEP` 档与 ChatGPT 的 `deep_research` 模式分别判断。

具体桥接操作使用现有 `chatgpt_request`、`chatgpt_status`、`chatgpt_result` 和
`chatgpt_continue`，详见
[chatgpt-consultation 指引](../../profiles/shared/chatgpt-consultation/SKILL.md)。
任务包至少说明：主题与问题、条件和重点、已知内容、缺口、已经尝试的找法、期望交付。
只发送相关片段，不发送完整知识库或无关个人资料。

请求关联当前有效且属于 Wisdom 的 UuMA Run，并保留主题、Orbit、问题、工具模式、
外部请求 ID、会话 URL、提交及更新时间。相同未完成任务查询原请求，不重复提交。
澄清或研究计划在原授权范围内可接续；新增范围或账户操作交回用户处理。

Deep Research 按长任务处理。短轮询超时表示结果尚未取得，保存请求并在后续周期回收。
重启从已保存的请求状态恢复；不因一个周期结束就丢弃报告，也不在提交不确定时盲目重发。
完整报告可保存为外部工具产物，重要结论仍需原始来源支持；报告和聊天记录不自动批准知识。

## 4. 没有新资料时的下一步

一次空结果，只说明某个工具在某种找法下没有返回匹配资料。
研究仍有价值、用户未暂停或停止且预算未耗尽时，Planner 应选择有理由的下一步：

- 修正问题表达，改变别名、语言、条件、时间范围或关键词。
- 让 ChatGPT 帮助分析搜索缺口和可能的出处，再验证这些线索。
- 使用适合的另一来源或工具模式，必要时发起 Deep Research。
- 沿已知资料的引用、原始机构或制造商追查。
- 对确实缺乏直接证据的分支保留缺口，推进其他有价值的分支。

每次选择记录理由及实际结果。无需机械地每轮调用全部工具，但不能在仍有相关且可用的
未尝试途径时宣称“已找尽资料”。重复无效查询应退避、换策略或换分支，避免消耗预算空转。
外部请求等待时间不算有效研究时间；提交、轮询及模型使用须按真实可取得的数据计量，
无法取得外部模型 token 用量时明确标记未知，不能伪报零或声称预算计量完整。

## 5. 状态、暂停与恢复

| 情况 | 状态与后续 |
| --- | --- |
| 已保存，等待执行或下一次回收 | `QUEUED`，显示待做工作和可取得的下次检查时间 |
| 正在检索、阅读、综合或处理工具结果 | `ACTIVE`，显示实际阶段；没有执行证据不能声称运行中 |
| 单轮没有新资料 | 调整策略或推进其他缺口；不自动转为 `PAUSED` |
| 用户要求暂停 | `PAUSED`，保留请求、成果、用量和恢复位置；重启不得自行恢复 |
| 达到任一预算上限 | `BUDGET_EXHAUSTED`，说明哪项用量达到哪项上限；不得自行追加 |
| 权限、登录、额度或依赖阻断所有有用的后续行动 | `BLOCKED`，说明具体原因、已尝试恢复、需要谁处理和后续安排 |
| 可恢复工具故障 | 保留失败原因，按现有有界重试策略重试；其他可用分支可继续 |
| 失败且恢复策略已用尽 | `FAILED` 或明确的 `BLOCKED`，说明失败及恢复入口 |
| 已达到知识满足条件 | `COMPLETED`，说明完成范围和仍然存在的限制 |
| 用户停止 | `STOPPED`，保持停止，不用新任务绕过 |

工具队列的 `PAUSED` 与主题 Orbit 的 `PAUSED` 分别呈现。一个工具需要账户恢复时，
先判断其他授权途径能否继续；无法继续才报告主题受阻。
“没有资料”“暂时没有证据”“请补充方向”本身不能作为自动暂停整项研究的充分原因。

任何停止执行的状态必须持久保存：原因类别、清楚的说明、发生时间、受影响的问题、
相关工具和请求、实际用量、剩余缺口、下一步，以及自动重试时间或恢复所需条件。
原因缺失时回答“记录缺少原因，需要诊断”，保留诊断问题，不猜测或补写一条假原因。

## 6. 正常聊天与进度查询

聊天始终可以继续，研究状态和 KAG 可用性不应阻断普通沟通。
“做到哪里？”“为什么停了？”“用了哪些途径？”“下一步是什么？”以及投诉和纠正，
读取已有主题与任务，不创建新主题、不创建同名研究问题、不重置预算。

回答至少让用户理解：正在研究哪个主题、已有成果、当前实际阶段或停止原因、
尝试了哪些途径及结果、哪些途径尚未尝试或不可用、下一步或需要处理的事项，以及文档链接。
用户问得简短时先给直接答案，再提供必要细节。工具结果为零与工具尚未提交必须分开说明。
无法确认的状态明确说尚未确认，不以“正在研究”安慰用户。

已有主题的重点调整和暂停／恢复／停止继续使用原任务。多个旧主题可能被指代时只询问
要控制哪一个。真正的新主题仍需先展示范围并取得用户同意。

首次实质成果、重要发现、修正、完成、预算耗尽和需要处理的阻断发送简短 digest，
包含原因、后续和固定链接。普通后台周期保持安静；通知失败保留 outbox 与失败原因，
不改写研究结果或伪称 Telegram 已交付。

## 7. 持久化及权限

复用 `uuma.db` 的 Run 和 ChatGPT 请求队列；未来工具的执行控制也遵循该边界。
`wisdom.db` 保存主题、问题、Orbit、资料、知识、文档版本，以及语义化的调用关联和用量。
两个库通过标识关联，不合并、不跨库联表；Hermes `state.db` 仅承担 Hermes 会话。
KAG 保持可重建投影。

来源、报告、证据、候选结论和研究任务保持不同类型。更正保留版本、原因和事件历史。
Wisdom 可提出知识修改；只有 Orchestrator／用户审查可以批准、应用、拒绝或反转。

4. 全量回归：`tests/test_orbit_planner.py`、`tests/test_orbit_runtime.py` 与 `tests/test_chatgpt_bridge.py` 共 94 项 pytest 契约及 ruff 校验全部通过。
