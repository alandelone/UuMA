Brainstormer 的职责

把模糊想法变成可讨论的问题，澄清假设、比较方案、挑战推理，再收敛成有依据的决策与可建造的产物。Persona、专业知识、Lens、Technique 和 Depth 由 SOUL 与技能指导，不能把这些概念画成已实现的独立后台服务。

持久工具覆盖上下文恢复、主题检索、事务提案、Decision Map、当前问题设置；可选容量计算器只验证给定场景的算术。其他 Agent 的结论仍需评估来源。

在 Observatory 中查看

  1. 让 Brainstormer 和 Observatory 使用同一个 UUMA_DATA_DIR。默认位置是 %LOCALAPPDATA%/UuMA。
  2. 已有服务时打开 Observatory。需要启动时使用仓库的 scripts/start-observatory.ps1，或 python -m uuma.observatory。
  3. 选择 Brainstormer 卡片。展开后可看主题、决策、问题、假设和检查点；默认展开最新主题，前 5 个之外用 Show More 查看。
  4. 在归属活动项中选 专案决策图谱 或 架构议题，右侧抽屉显示对应详情。主题支持全部展开 / 折叠。
  5. 在动态流用 Brainstormer 筛选，查看带 profile 标识的真实审计活动。

依据：前端主题展示、卡片与活动项选择。

数据路径

什么才会出现在卡片里

brainstormer/projects/<project_id>/state.json → BrainstormerAdapter → /api/observatory/agents → 卡片与检查抽屉。

Adapter 直接读取 JSON 并按主题归类。它没有调用 Store 的完整推进队列投影，也没有调用 8772 的审核、提交或焦点 API。

无正式项目状态时，后端会退到 Hermes 会话，再退到待机条目；前端也含示例主题与修订号。因此，卡片可见或显示 ACTIVE 不能单独证明真实运行或已保存决策。

依据：正式投影、回退来源。

如何理解审核

Brainstormer 提案；Store 保护正式状态。项目、主题、决策、SUPERSEDE 和触及既有决策的链接变更需要 Orchestrator / 用户审核。安全的假设、问题、证据与检查点可通过安全提交。

对象修订冲突与 DAG 循环会阻止应用；推理结论不能自动升级为外部事实。

实时与持久化边界

SSE 初连发送工作区快照，后续主要推送活动事件。前端仅在 SSE 断开时每 10 秒轮询卡片；显示状态需核对来源与修订号，必要时重新加载。

Worker MCP 与 State Daemon 都可调用 Store。当前锁为进程内锁；不能把 Daemon 描述成所有写入都必须经过的单写者。
